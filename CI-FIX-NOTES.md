Fixed (statically verified against the sources; not run, no Gradle/network here):

The test now uses a control character (`\u0007`) as the illegal key. Pool behaviour unchanged.
- `ProviderStoreTest.probeGoesThroughTheRealAdapterWithHeaders`, `probeLeavesRoomForAToolCall`, `ModelSetupNetworkTest.customResponsesListsThenProbesTheResponsesEndpoint` — a real product bug, not a test bug. The key-pool change made `ProviderStore.buildModel` pass `keySupplier = { activeApiKey(cfg.providerId) }` to every adapter, and the adapters use the supplier instead of the `apiKey` argument whenever it exists (`resolveKey()`; `ResponsesModel` throws `ModelError.Auth` on a blank pooled key). The connection probe builds a throw-away provider (`"probe"`) with no stored key, so the key the user had just typed was never sent. `buildModel` now uses `currentKey`: the pool key, and only when the provider has no stored key at all, the `apiKey` passed in. Saved providers behave as before (cooldowns and rejections still apply). Each key is still tried once per request, so no retry loop.
- CI: new step `Check bundled runtime asset` in the `app` job prints size / sha256 / magic bytes / git eol of `rootfs.tar.xz` next to the constants in `BundledRuntime.kt`, and fails early.

Not fixed — need the real runner or more data:

- `BundledRuntimeTest` x2: **root cause found in run `08a23f6`.** `app/src/main/assets/runtime/rootfs.tar.xz` in the commit is a 133-byte Git LFS pointer (`version https://git-lfs.github.com/spec/v1`, `oid sha256:250e9fbe…`, `size 57957216`), not the 57,957,216-byte file. Its sha256 on CI (`9537748d…`) is exactly the sha256 of that pointer text. The repo has no LFS config and checkout uses `lfs: false`, so the pointer is what tests see. The real file in the uploaded source is fine. Fix on the repo side: commit the real binary instead of the pointer (see "Recommit the runtime" below). The CI step now says so explicitly, and no longer blocks the other tests (`continue-on-error`).
- `core`: 16 `LoopScenarioTest`, 3 `PromptSurfaceTest`, 1 `SystemPromptAssemblyTest` snapshot mismatches — regenerate with the commands in the first section.

### Recommit the runtime (bypass any LFS filter on the machine that pushes)

```bash
git show HEAD:app/src/main/assets/runtime/rootfs.tar.xz        # should print the pointer text
git -c filter.lfs.clean=cat -c filter.lfs.smudge=cat -c filter.lfs.process= -c filter.lfs.required=false \
    add --renormalize app/src/main/assets/runtime/rootfs.tar.xz
git cat-file -s :app/src/main/assets/runtime/rootfs.tar.xz     # must print 57957216
git commit -m "Store the bundled runtime as a regular file, not an LFS pointer"
```

If that size is still 133, the filter comes from `.git/info/attributes`, which beats `.gitattributes`: remove the lfs line there. The 58 MB file is under GitHub's 100 MB limit (it warns above 50 MB).

### No terminal? (phone workflow)

- `ci.yml` has a step that, when the commit holds a pointer, asks GitHub's LFS batch API for the object, checks its sha256 and replaces the pointer (the first attempt, `git lfs pull`, downloaded nothing in run `b731682`). If GitHub has no such object the job log prints the server's answer: then the object was never uploaded and the real file must be committed. GitHub LFS free bandwidth is about 1 GB/month, so each CI run costs about 58 MB; recommitting the real file is still the lasting fix.
- New workflow `.github/workflows/update-snapshots.yml` (Actions → Update snapshots → Run workflow) regenerates the core snapshots in CI and pushes them to a branch `ci/update-snapshots-<run_id>`, not to main. Review Files changed there before merging.
- The `core` job now has a step `Show failed test diffs` (runs on failure) that writes each failed test's expected/actual message to the run's Summary page, so the snapshot differences can be read on a phone without downloading `core-test-results`.
